# ServiceCrew — Task Tracker

Live status for every build task in `ServiceCrew-Plan-v2.md`, broken out from each phase's "Builds:" list. This file is the source of truth for what's done — conversation history can be compacted or lost, this file can't. Anyone (or any fresh session) opening this repo should be able to read this file and know exactly where the build stands, with zero dependence on chat memory.

**Update this file, don't just remember the status.** Mark a task's row when it's implemented, and again once the user has manually verified it — don't mark a task `done` without that manual check.

## Status values

| Value | Meaning |
|---|---|
| `not-started` | Nobody has picked this up yet. |
| `built` | Task implemented, awaiting the user's manual check. |
| `done` | User has manually verified it works. Task is complete. |

A phase's `Phase review` row is set to `done` once the user has reviewed the whole phase.

### V1's actual Phase 1d build: the employee job-status page

Email-based stand-in for the deferred crew PWA, built this session:

- **Migration**: `sc_booking_assignments` gains `status_token_hash`/`status_token_expires_at` (`SERVICE_CREW_DB_VERSION` → `1.5.0`) — same "stored hashed, single-purpose" token rule as `Service_Crew_Payments`' pay tokens, but TTL'd to the job's own scheduled date (+14 days buffer) rather than a fixed duration from send time, since the link needs to survive until the job is actually done.
- **`Service_Crew_Assignments::generate_status_token()`/`find_active_assignment_by_status_token()`** — the lead's token is (re-)generated every time `assign_crew()` runs, so the link in the most recently sent email is always the one that works; a token's assignment must still be `STATUS_ACCEPTED` to resolve, so swapping out a lead automatically invalidates their old link with no extra bookkeeping.
- **`Service_Crew_Bookings::update_job_status()`/`complete_job()`** — new `STATUS_ON_THE_WAY`/`STATUS_IN_PROGRESS` statuses; transitions are deliberately lenient about prior status (an employee who skips a step doesn't get stuck) and share the existing `sc_booking_status_changed` action, so `Service_Crew_Emails`'s dispatcher (generalized from a `cancelled`-only `if` to a status→template map) now also fires the already-existing-but-dormant `on_the_way_customer`/`started_customer`/`completed_customer` templates — whether the transition came from this page or the admin's own status dropdown.
- **New `includes/class-service-crew-uploads.php`** — the quote form's hardened photo-upload validation (extension+MIME sniff, `getimagesize()` re-check, size cap, `wp_handle_upload()`) extracted verbatim into a shared choke point, since the job-status page's completion photos needed the exact same validation and duplicating security-sensitive upload code across two files was a real drift risk. `class-service-crew-quotes.php` refactored to call it too — behavior unchanged, verified line-by-line.
- **`public/class-service-crew-job-status-page.php`** (new) — same "renders on `?sc_job=<token>` via `template_redirect`, no WP Page/rewrite-flush needed, fully outside the active theme" pattern as the existing pay page. Shows the job summary and, based on current status, the one next action: On the way → Start → Complete (+ optional note and up to 6 photos). No Accept/Decline (no accept step in V1) and no job *list* (the link is always for one specific job).
- **New `includes/class-service-crew-job-status-controller.php`** — public, token-gated `POST /job-status/{token}/on-the-way|start|complete`.
- **`Service_Crew_Emails::on_booking_assigned()`** now takes the lead's plaintext status token as a 4th arg (passed through `sc_booking_assigned` the one time it's available — tokens are never recoverable after generation) and appends a status-link section to the lead's copy of the `assignment_details_employee` email only; other team members' copies omit it.
- **Not built**: the admin push-notification channel (see V1 note above).

**Built this session (2026-10-04).** This is the exact same category of hand-rolled Web Push crypto (VAPID keypair, ES256 JWT signing, no library) that was explicitly skipped once before for the deferred crew/vendor PWA — see Phase 1d's own note: "no library and no way to test it against a real push service in this environment." Reversed back on for this feature specifically (admin alerts only) as one of Phase 2's four locked decisions. Given that history, a crypto spike ran *before* writing any real code, to confirm the approach was actually viable here rather than building blind:

- **Spike finding, now baked into the implementation**: this project's own local Windows/Laragon PHP build has a broken `OPENSSL_CONF` (its compiled-in default path, `C:\Program Files\Common Files\SSL\openssl.cnf`, doesn't exist on this machine) — `openssl_pkey_new()` for an EC key fails outright with `error:80000003:system library::No such process` unless given an explicit config. A `putenv('OPENSSL_CONF=...')` from within PHP is too late (OpenSSL loads its config at process init, before user code runs) — the fix that actually works is passing `'config' => <path>` directly in `openssl_pkey_new()`'s/`openssl_pkey_export()`'s own options array, confirmed via a standalone spike script (keygen → PEM export → ES256 sign → DER-to-raw signature conversion → signature round-trip verify, all passing). A copy of OpenSSL's own stock example config is now bundled at `includes/openssl-vapid.cnf` and passed explicitly on every call — harmless on a server where `OPENSSL_CONF` was already fine, fixes it everywhere it wasn't.
- **`includes/class-service-crew-agent-push.php`** (new): `get_or_create_vapid_keys()` generates an EC P-256 keypair once (`sc_agent_vapid_keys` option) and never regenerates it (would invalidate every existing subscription). `build_vapid_jwt()` signs a standard RFC8292 JWT (`aud`/`exp`/`sub` claims) — `openssl_sign()` only produces a DER-encoded signature, so `der_to_raw_ecdsa_signature()` hand-parses the ASN.1 structure and repacks it as JOSE's raw `r‖s` format (no library). `send_to_all_subscriptions()` sends an **empty-payload** push to every stored subscription (`Content-Length: 0`, no RFC8291 payload encryption at all — deliberately, per the original design decision) and deletes any subscription the push service responds to with 404/410 (the standard "this subscription is dead" signal). Fired from the already-existing `sc_agent_escalation_created` hook (Phase C) — push and the admin email/bell are independent channels, not gated by each other.
- **`public/js/agent-push-sw.js`** (new) — the service worker itself: shows one static notification on `push` (no event-specific detail, since no payload travels), opens the Agent screen on click. Served at the root-relative `/sc-agent-sw.js` (not under this plugin's own directory, so the registration's default scope covers the whole site) via a `template_redirect` exact-path match — **deviates from this row's own original "`add_rewrite_rule()`" wording**, reusing the simpler, already-established `Service_Crew_Pay_Page`/`Service_Crew_Job_Status_Page` pattern instead (no rewrite flush needed). Caught and fixed a real bug this way: WordPress marks any URL that doesn't match a rewrite rule as a 404 *before* `template_redirect` ever runs, so the response's body was correct but its HTTP status silently stayed `404` — fine for a curl check, but the Service Worker spec requires a 2xx status for `register()` to succeed, so this would have **silently broken the entire feature in a real browser** despite every other check passing. Fixed with an explicit `status_header(200)`; confirmed via a real `curl` request against the live local site (now `200`, correct `Content-Type`, survives a query string, doesn't affect any other page's status).
- **Admin UI** (`admin/js/app-agent.js`'s new "Push notifications" card) — registers the service worker, fetches the VAPID public key (`GET /agent/push-vapid`), subscribes via `pushManager.subscribe()`, and posts the resulting subscription to `POST /agent/push-subscribe`. Degrades to a plain explanatory message (no broken button) when the browser lacks Push API support, or when the site isn't served over HTTPS/`localhost` — Push API refuses to work in either case regardless of anything this plugin does, and this dev site is neither.
- **Verified end-to-end against the live local site**, same temporary-CLI-script convention as every other phase: migration, key generation/persistence (including "calling twice returns the same keys, never regenerates"), full JWT structure/signature correctness (64-byte raw signature, correct `aud`/`exp`/`sub`), the subscribe/unsubscribe REST logic (including upsert-by-endpoint and rejecting an invalid subscription), and — via a mocked `pre_http_request` filter rather than a real network call — the exact outgoing push request shape (VAPID-shaped `Authorization` header, `TTL` header, zero `Content-Length`/empty body) and the 404/410 auto-cleanup actually removing the subscription row. Separately confirmed the service-worker-serving fix via a real `curl` request against the live site. PHP lint clean on every touched file; `node --check` clean on both touched JS files.
- **What could not be verified here, and why — a hard limitation of this environment, not a gap in the work**: actual push delivery to a real subscribed browser, and the notification/click behavior in that browser. This needs a real HTTPS-or-localhost origin and a real browser with Push API support, neither of which this local HTTP dev environment provides, and no browser automation tool is available in this project regardless (consistent with every other front-end feature built this session). **Before calling this phase `done`, a manual pass on a real HTTPS site is needed**: open the Agent screen, click "Enable notifications," grant the permission prompt, trigger an escalation from another browser/incognito session, and confirm a real OS-level notification appears and clicking it opens the Agent screen.
